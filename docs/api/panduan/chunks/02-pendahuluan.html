1. Pendahuluan

1.1 Tentang Web Service myUnila

Web Service API myUnila adalah layanan integrasi data internal Universitas Lampung yang menyediakan akses terstandar ke data akademik, kepegawaian, kerjasama, tracer study, dan referensi. Dibangun berdasarkan arsitektur REST dengan format JSON, layanan ini ditujukan untuk dipakai oleh aplikasi internal Unila (Sistem Informasi Akademik, Sistem Penjaminan Mutu, Sistem Kepegawaian, Dashboard Pimpinan, dll.) maupun aplikasi mitra resmi yang telah disetujui oleh UPA TIK.

Layanan ini menggantikan API legacy /v1/pdrd/* dengan struktur grouping baru per-domain (/v1/mahasiswa, /v1/sdm, /v1/pegawai, /v1/penelitian) yang lebih konsisten. URL lama tetap dipertahankan untuk kompatibilitas mundur namun dianggap deprecated.

Penting — Endpoint Publik vs Protected:

1.5 Kong API Gateway

Semua request dari konsumen tidak langsung ke service backend Go, melainkan melewati Kong API Gateway sebagai entrypoint tunggal. Pola URL: 

{kong_base}/{service_name}/{path_belakang}
       └─ Kong route                  └─ diteruskan ke backend

Contoh:

https://my.unila.ac.id/api-service/v1/auth/login
↓
Kong Gateway (HTTPS) → forward ke service backend (HTTP, internal) → /v1/auth/login

Apa yang Kong lakukan untuk setiap request:

  1. Routing — match URL pattern ke service backend yang sesuai
  2. Strip prefix — buang segmen /api-service sebelum forward
  3. Rate-limit check — pakai counter Redis, deny kalau over-quota
  4. Header injection — tambah X-Real-IP, X-Forwarded-For untuk audit log
  5. SSL termination — handshake HTTPS di Kong, traffic internal HTTP
  6. Logging — record latency, status, response size ke metrics dashboard
Implikasi untuk konsumen: selalu pakai URL Kong publik (https://my.unila.ac.id/api-service/...). Jangan mencoba akses langsung ke service backend internal — itu bypass rate-limit, audit log, dan policy security.

1.6 Rate Limiting

Untuk melindungi infrastruktur dari beban berlebih (intentional / accidental DDoS, query loop bug, dst), Kong menerapkan rate-limit per-IP. Konsumen wajib memperhitungkan limit ini saat merancang integrasi.

SkenarioLimitWindowPolicy
Default per-IP (anonymous)60 request1 menitlocal (per Kong node)
Per-konsumen authenticated120 request1 menitlocal
Endpoint berat (foto, list besar)20 request1 menitlocal
Whitelist mitra (atas permintaan)1000 request1 menitcluster-wide (Redis)

Header Response Rate-Limit

Setiap response (sukses maupun gagal) menyertakan header rate-limit standar dari Kong:

HTTP/1.1 200 OK
X-RateLimit-Limit-Minute: 60
X-RateLimit-Remaining-Minute: 47
RateLimit-Reset: 23
...
HeaderArti
X-RateLimit-Limit-MinuteBatas total request per menit
X-RateLimit-Remaining-MinuteSisa kuota dalam window berjalan
RateLimit-ResetJumlah detik sebelum window di-reset

Saat Limit Tercapai (HTTP 429)

HTTP/1.1 429 Too Many Requests
Retry-After: 38
Content-Type: application/json

{
  "message": "API rate limit exceeded"
}

Header Retry-After berisi jumlah detik konsumen harus tunggu sebelum mencoba lagi. Implementasikan exponential backoff: 

// Pseudocode
let backoff = 1000;  // mulai 1 detik
while (true) {
  const res = await fetch(url, { headers });
  if (res.status !== 429) break;
  const retryAfter = parseInt(res.headers.get("Retry-After")) * 1000;
  await sleep(Math.max(retryAfter, backoff));
  backoff = Math.min(backoff * 2, 60_000);  // cap 1 menit
}
Praktik baik untuk batch import / sync:
  • Pakai limit=100 (max) untuk minimasi jumlah call.
  • Sleep 100-500ms antar request supaya tidak overshoot 60/menit.
  • Gunakan filter spesifik (mis. id_thn_ajaran) ketimbang fetch all.
  • Kalau butuh volume lebih dari default, ajukan whitelist via dev@unila.ac.id.

1.7 Prasyarat & Cara Mendapatkan Akses

1.7.1 Akses Endpoint Publik (Tanpa Registrasi)

Endpoint pada group dashboard (statistik agregat KTW lulusan) bersifat publik dan tidak memerlukan registrasi. Konsumen cukup mengikuti rate-limit standar per-IP (60 request / menit). Pemakaian khas: web profil universitas, infografis publik, integrasi dashboard pihak ketiga. 

// Tidak perlu Authorization header
curl https://my.unila.ac.id/api-service/v1/dashboard/ktw/overview?cohort=2018&jenjang=S1

1.7.2 Akses Endpoint Protected (Wajib Registrasi)

Untuk seluruh group selain dashboard, konsumen harus melalui empat tahap:

  1. Pendaftaran aplikasi — aplikasi konsumen diregistrasi oleh tim UPA TIK, menghasilkan id_aplikasi (UUID) dan app_key identifier.
  2. Penetapan PJ Aplikasi — Penanggung Jawab ditunjuk & mendapat akun pengguna (username + password) di sistem manajemen akses.
  3. Penetapan peran Developer — PJ harus memiliki peran Developer (id_peran = 107) di organisasi Universitas Lampung. Tanpa peran ini, endpoint /v1/auth/login akan menolak dengan HTTP 403.
  4. Otorisasi per-endpoint — administrator UPA TIK memberikan akses ke endpoint spesifik yang dibutuhkan via menu WS Authorization.
